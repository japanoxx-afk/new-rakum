=====================================================

비밀번호·토큰은 여기에 적지 않는다. 운영안내 원문(서버 소유자 제공)은 저장소에 넣지 않는다.

1. 목표
-------
런처가 로컬(127.0.0.1)에서 띄우는 라크무 서버(저장소 루트 server.py)를 서버 소유자가 제공한
Synology NAS + Debian VM(Docker, Portainer, 2 vCPU, RAM 2GB)에서 24시간 운영한다.
사용자는 외부에서 웹(File Station :5001, Portainer :9443)으로만 접근한다. SSH 없음.

4. 구조·결정과 이유
-------------------
- 이미지: 공개 python:3.12-slim. 빌드가 필요 없다. 운영안내상 File Station 의 Dockerfile 을 Portainer 가 자동
  빌드하지 않으며, Portainer 에서 이미지 빌드/레지스트리 사용 가능 여부는 확인되지 않았다.
  server.py 는 표준 라이브러리만 사용 → 코드 폴더 마운트 방식이 가장 단순. (slim 은 tzdata 포함 → TZ=Asia/Seoul 적용)
- 코드 위치: NAS game-servers/rakmu-live/app (VM /mnt/game-servers/rakmu-live/app, 컨테이너 동일 경로)
- 데이터: game-servers/rakmu-live/data — matches.json(최근 500판), server.log(1MB×6), game_rules.json(선택, 서버가 읽기만 함)
- 볼륨: 외부 볼륨 game_servers_data 를 /mnt/game-servers 에 통째로 마운트(운영안내 지시대로 기존 외부 볼륨 참조).
  공유 폴더 전체가 보이므로 nas_entry.py 가 rakmu-test 를 데이터 폴더로 쓰는 것을 거부한다.
  개선 여지: Docker Engine 26+ / Compose 2.26+ 이면 volume.subpath: rakmu-live 로 rakmu-live 폴더만 마운트 가능 (버전 확인 필요).
- 네트워크: bridge + 포트 게시 (rakmu-test 는 host). 이유: 컨테이너 안 포트를 server.py 기본값(11223/11225/47584)
  그대로 두고 외부 번호만 compose 변수로 바꿀 수 있고, 다른 게임과 격리된다. 외부→VM 인바운드는 DNAT 이라
  서버가 보는 클라이언트 IP 는 실제 공인 IP 로 유지된다(확인 필요: 실제 배포 후 로그의 Connected: 줄).
- 포트 변수: LOBBY_PORT(기본 30010, TCP→11223), HTTP_PORT(30011, TCP→11225), RELAY_PORT(30012, UDP→47584)
- 자원 제한: mem_limit 128m, cpus 0.5, pids 64, read_only 루트 + /tmp tmpfs 16m (security_opt no-new-privileges 는 Portainer 비관리자 제한으로 제거),
  도커 로그 json-file 5m×3. privileged/도커 소켓/호스트 경로 마운트 없음.
- healthcheck: 컨테이너 안에서 http://127.0.0.1:11225/version (로비 TCP 로 하면 60초마다 접속 로그가 남아서 피함)
- nas_entry.py 환경변수: RAKMU_DATA_DIR, RAKMU_LOBBY_PORT, RAKMU_HTTP_PORT, RAKMU_RELAY_PORT(수신만 바뀜,
  릴레이 목적지는 47584 고정), RAKMU_LOG_MAX_BYTES, RAKMU_LOG_BACKUPS.
  nas_entry.run() 은 server.main() 을 복제한 것이다. server.py 의 main()/HTTP 시작부가 바뀌면 같이 맞출 것
  (참조: server.HOST, PORT, HTTP_PORT, UDP_RELAY_PORT, _HistoryHandler, DP8RelayProtocol, ClientSession, STATE, log).
  test_nas_entry.py 가 루트 server.py 로 실행되므로 깨지면 시험이 실패한다.

5. 포트·경로 요약
-----------------
ports.txt 참고. 공유기는 TCP/UDP 30000~30999 를 VM(내부 192.168.0.94)의 같은 번호로 전달.
기존 rakmu-test: TCP 30000 로비, TCP 30001 전적·버전, UDP 30002 방 찾기, host 네트워크.
rakmu-test 의 실제 compose/코드는 확인하지 못했다(확인 필요). 사용자가 Portainer 에서 Editor 내용을
비밀값을 지우고 보여 주면 비교 가능. game-servers/rakmu-test/data 는 보존(읽기/쓰기 안 함).

클라이언트 고정 포트(코드 근거):
  Rhakmu.exe 로비 TCP 11223 (SYNC_PORT_ANALYSIS.txt: 소켓 생성부 push 0x2bd7), 게임 P2P UDP 11223
  launcher.py: http://{ip}:11225/rules, /matches.json, /ranking (_sync_rules_from_server, 전적 조회)
  WG_IPX.dll EnumHosts 방송 UDP 47584
→ 현 런처/게임은 NAS 의 30000번대 포트에 바로 접속할 수 없다.

(4) 인터넷 너머 대전(P2P) 문제 — 핵심 후속 과제:
    server.py 는 방 host_ip / address_for() 에 "서버가 본 접속 IP"를 쓴다(_handle_create_room, address_for).
    NAS 에서는 이것이 플레이어의 공인 IP → 게임 P2P(UDP 11223)와 DP8 이 공유기에 막힐 가능성이 높다.
    또 DP8RelayProtocol 은 VPN 브로드캐스트를 받아야 동작하므로 NAS 에는 패킷이 오지 않는다.
    방안: 플레이어들은 계속 Radmin VPN 을 켜고, 런처가 자신의 VPN IP 를 서버에 알림
          (예: HTTP POST /announce {account, vpn_ip} 또는 로비 접속 직후 별도 패킷) → 서버가 host_ip/address_for 에
          그 주소를 사용. UDP 47584 방송은 런처(또는 기존 radmin_session)가 로컬에서 캡처해 VPN 상대에게 직접 보내는 방식 검토.
          새 HTTP 쓰기 API 를 만들면 인증 없이 공개하지 말 것(운영안내). 공유 토큰을 쓰면 Portainer 환경변수로 넣고 저장소에 넣지 않는다.
    이 작업 전까지 NAS 서버는 "로비·채팅·전적 서버" 수준으로 본다. 실제 대전 성공은 사용자 시험으로만 판정.
    → 2026-11-21 사용자 보고로는 NAS 서버로 게임이 정상 동작(전적에 2인전 기록 있음). 어떤 VPN 조합에서 됐는지는 미기록.

7. 복구 방법
------------
- 서버가 이상하면: Portainer → Stacks → rakmu → Stop. 데이터는 rakmu-live/data 에 남는다.
- 코드 롤백: rakmu-live/backups/app-YYYYMMDD → rakmu-live/app 덮어쓰기 → Start (README 5장).
- 데이터 복원: Stop → backups/data-YYYYMMDD/matches.json → data/ → Start.
- 스택 완전 제거: Stacks → rakmu → Delete (외부 볼륨 game_servers_data 와 NAS 파일은 지워지지 않는다.
  "Remove volumes" 같은 선택지가 나오면 체크하지 않는다).
- rakmu-test 를 멈췄던 경우: rakmu 를 Stop 하고 rakmu-test → Start. 대체 전에 저장해 둔 rakmu-test 설정으로 되돌린다.
- 로컬 방식으로 복귀: 런처는 지금도 그대로 로컬 server.py 를 쓰므로 아무것도 바꿀 필요 없다.
