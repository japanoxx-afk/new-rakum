4D7A80 Game_Multi:
  4D7ABA sets sync manager+48 to 4 (existing configurable buffer).
  4D7AC0 WND_GetMessage drains message queue, not just one message per frame.
  4D7B63 Mouse_Proc and 4D7B68 KeyBD_Proc run each outer iteration.
  4D7B8F..9F tests B412B4 % 5 == 0. Only that branch calls GMPKSend_SyncData
  at 4D7BA1. Thus command batch construction is once per five outer frames.
  4D7BBB..DB compares local slot+62 with latency+48 before receive/consume.
  4D7BE3 calls 44A840 then 4D7BEE calls 449AB0 (slot synchronization check).
  4D7C3A..86 enforces elapsed-frame timer B412B8. No timing change proposed.

4494C0 command enqueue:
  allocates node and payload; copies current command from manager+44;
  stores ordering stamp 1069E94; inserts sorted queue (manager+4 is head).
4496C0 batch construction:
  checks paused flag manager+10; copies packet, assigns manager+38 sequence,
  increments sequence, drains ALL queued commands and appends checksum;
  calls local 449210 and sends remote packets. Calling this again on clicks
  would advance sequence/close a batch early, NOT merely flush a socket.
  Therefore an immediate-send patch would change simulation schedule.
449210 accepts numbered packet into 32-slot ring. A packet revision mechanism
would require review of duplicate/out-of-order handling and all peers.
44A840 calls UDP receive 449D80, builds active/ready masks and dispatches
44AA66 calls the empty base stub 448300; actual command processing is at
44AABC via GMPKRecv_Handling (4407E0). This is distinct from visual feedback.

Conclusions so far:
  User's 1-turn responsiveness / multiplayer slowdown is consistent with
  insufficient packet safety buffer, not proof of a TCP queue bottleneck.
  Do not silently change modulo-5, buffer=4, tick limiter, sequence numbers,
  or repeat same-turn sends. No demonstrated unnecessary 0.5-second wait found.
  Rendering changes do not eliminate the explicit lockstep command buffer.
  Need real frame, batch, queue and consumer counter timing before selecting
  an optimization. Sampling is not a breakpoint trace and may miss short-lived
  queue nodes; batch construction is not on-wire or visible unit-action time.

  The target batch is inferred from current next-sequence, NOT matched against
  command payload. These are queue/counter estimates, not exact mouse-to-visible

  Four-turn fixed pipeline, not redundant network/sleep waiting, dominates.
  Removing its delay while preserving the same execution schedule is impossible.
  Changing batch cadence is another hypothesis, separate from prediction/rollback.
  No formal launcher release made from this observation.

Cross-project comparison and offline experiment:
  Changpogo's documented user-confirmed 75ms improvement separates communication
  cadence from simulation credit. Its scheduler cannot be copied into RhakMu.
  RhakMu Game_Multi calls world/unit processing (4A1860 / 43D970) before the
  modulo-five branch, every outer frame. Sync marker 2000 at 44091D stores the
  comparison value, decrements queued-sync count and clears the ready mask;
  it does not itself execute a world tick. Therefore shorter command batches
  deserve testing without changing outer-frame pacing or configured buffer=4.
  command_cadence_trial.py changes only MOV ECX,5 to MOV ECX,3 at 4D7B96.
  Nominal cadence 165 -> 99ms; three buffered intervals 495 -> 297ms.
  These are theoretical cadence estimates, NOT measured improvement.
  Native-branch emulation verifies both cadences, unchanged buffer gating and
  continued checksum-check call. Three tests pass. Only one byte changes.
  All peers MUST use the same cadence. Shorter time coverage of the four-batch
  buffer could cause stalls on high-jitter links, despite unchanged turn count.
  Sync marker generation also calls 4C9C10 more often; its effect and cross-peer
  checksum determinism still require gameplay validation. No claim of identical
  gameplay/random sequence, real-world speed or multiplayer safety is made.
  This is an offline opt-in trial, never automatically applied by the launcher.
